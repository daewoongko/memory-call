# Codex 작업 지시 — `일정·복약` 탭 재설계

**목업: `docs/mockups/medication_tab.html`** — 브라우저로 열어서 보고 시작할 것.
세 화면의 구조·문구·색 역할이 전부 들어 있다. 이 문서는 그 목업의 근거와
데이터 설계를 설명한다.

`docs/analysis_design.md`(특히 3장 약–관찰 연결, 15장 안전 문구 규칙)를 따른다.

> **범위 변경 — `docs/codex_prompt_checklist.md`를 먼저 읽을 것.**
>
> `체크사항` 탭이 신설되면서 **여정 A(오늘 확인할 관찰)는 그 탭으로 옮겨간다.**
> 두 곳에 같은 목록을 그리면 안 된다.
>
> | 탭 | 역할 |
> |---|---|
> | 체크사항 | **무엇을 할지** — 할 일 단일 목록 (여정 A) |
> | 일정·복약 | **어떻게 할지** — 관찰 체크리스트 실행, 증상 역조회(여정 B), 약 정보, 달력 |
>
> 따라서 이 문서에서 **여정 A의 "오늘 확인할 관찰" 목록 화면은 만들지 않는다.**
> 체크리스트 실행 화면(목업 2번째)과 증상 역조회(목업 3번째)만 이 탭에 만든다.
> 목업 1번째 화면은 체크사항 탭의 디자인 참고로 넘긴다.
>
> 4장의 매핑 테이블과 2장의 안전선은 **두 탭 모두에 그대로 적용된다.**

---

## 1. 왜 바꾸나

지금 탭은 **약을 나열하고 그 아래 관찰 항목을 다는** 구조다. 그런데 요양사는
약을 보러 오지 않는다. **"오늘 뭘 확인해야 하나"**를 보러 온다. 순서가
사용자의 일 순서와 반대라서 복잡하게 느껴진다.

**방향을 뒤집는다: 약 → 관찰 이 아니라, 관찰 → 약.**

---

## 2. 안전선 (가장 먼저 읽을 것)

증상을 고르면 약을 보여주는 기능은 자칫 **부작용 원인 판정**이 된다. 그것은
의료 판단이며 CLAUDE.md 규칙 5(복약 지시 금지) 위반이다.

| ❌ 금지 | ✅ 허용 |
|---|---|
| "어지럼은 레보도파 때문입니다" | "어지럼은 레보도파와 리바스티그민의 **등록된 관찰 항목**에 해당합니다" |
| "약을 줄여야 합니다" | "이 약의 보고 기준: *실신·반복 낙상 → 신속 보고*" |
| "부작용이 의심됩니다" | "관찰된 내용이 등록 기준에 해당합니다" |

**시스템은 대조만 한다. 원인 판단과 처방 조정은 의료진의 몫이다.**

이 문장을 화면에 고정 문구로 넣는다(목업의 두 군데 참고). 나중에 누가
손대도 선이 무너지지 않게 UI에 박아 둔다.

## 3. 세 여정

### 여정 A — 출근 직후 "오늘 뭐 봐야 하지" (정기)

```
주 단위 날짜 스트립
  ↓
오늘 확인할 관찰  3건        ← 메인
  ● 박순자 · 레보도파      7일 주기 도래   AI 관찰 3건
  ● 이정호 · 클로피도그렐   7일 주기 도래
  ○ 박순자 · 리바스티그민   3일 남음
  ↓  (누르면)
관찰 항목 체크리스트  [있음 | 없음 | 확인 못함]
  ↓
medication_reviews 에 저장
```

**"도래"는 계산한다.** `medications.review_interval_days`와
`medication_reviews`의 최근 `review_date` 차이로 판정한다. 하드코딩하지 않는다.

### 여정 B — 라운딩 중 이상 발견 (역방향, 이번 작업의 핵심)

```
증상 칩 선택: [어지럼]
  ↓
이 어르신에게 등록된 약 중 '어지럼'이 관찰 항목인 것  2개
  ┌ 레보도파/카비도파   처방 목적 / 관찰 항목 / 보고 기준
  └ 리바스티그민 패치    처방 목적 / 관찰 항목 / 보고 기준
  ↓
[관찰만 기록] 또는 [기록하고 의료진 보고]
```

**증상 하나가 여러 약에 걸리는 것이 정상이다.** 하나로 좁히지 말고 전부
보여준 뒤 판단을 넘긴다. 좁히는 순간 원인 판정이 된다.

### 여정 C — AI가 먼저 잡아둔 것 (차별점)

여정 A의 체크리스트에 **AI 통화 관찰이 미리 채워져 있다.**

```
기립 시 어지럼   [AI 관찰 2건]
  "자리에서 일어나니까 어지럽고 넘어질 것 같다"   09:14
  "일어설 때 핑 돈다"                          11:32
  [있음] [없음] [확인 못함]
```

요양사가 라운딩 가기 전에 후보를 받는다. **빈 종이에서 시작하지 않는다.**
`backend/analysis/medication.py`가 이미 신호↔약을 잇고 있으나 화면이 없다.

## 4. 데이터 설계 — 한 테이블로 양방향

### 4-1. 핵심: 매핑은 **등록**이지 자동 추론이 아니다

`medications.monitoring_points`는 지금 자유 텍스트 배열이다.

```json
["기립 시 어지럼", "갑작스러운 졸림", "환시·혼란 변화", "보행 동결"]
```

이 문자열을 검색해서 증상을 찾으면 깨진다. 대신 **관찰 항목 하나하나를
표준 신호에 연결한 매핑 테이블**을 만든다.

```
schedule_id              signal                 monitoring_text      tier
med_sunja_levodopa       dizziness              기립 시 어지럼        monitoring
med_sunja_levodopa       hallucination_report   환시·혼란 변화        escalation
med_sunja_levodopa       fall_reported          보행 동결            escalation
med_jeongho_clopidogrel  bleeding_signal        멍·코피·잇몸 출혈     escalation
```

- `signal`은 `backend/analysis/observation_catalog.py`의 76개 신호를 그대로 쓴다.
  **새 어휘를 만들지 않는다**
- `tier`는 `monitoring`(경과 관찰) / `escalation`(보고 대상) 두 값

### 4-2. 같은 테이블을 두 방향으로 읽는다

| 여정 | 쿼리 | 결과 |
|---|---|---|
| A 체크리스트 | `WHERE schedule_id = ?` | 이 약의 관찰 항목들 |
| B 역조회 | `WHERE signal = ? AND elder_id = ?` | 이 증상이 걸린 약들 |
| C AI 선입력 | 위 결과 × 오늘 관찰된 신호 | 미리 채울 항목 |

**테이블 하나로 세 화면이 다 나온다.** 별도 인덱스를 더 만들지 말 것.

### 4-3. 체크 결과 저장

`medication_reviews`가 이미 있다(`severity`, `observed_flags`, `note`).
체크리스트 결과를 `observed_flags`에 JSON으로 넣고 `review_date`를 기록하면
여정 A의 "도래" 계산이 자동으로 갱신된다. **새 테이블을 만들지 말 것.**

### 4-4. 아직 받지 못한 것 — 약 기준표

사용자가 약별 기준표를 곧 첨부한다. 받기 전까지는 시드의 6개 약으로
구조만 잡는다. 표를 받으면 **출처와 지위를 반드시 구분**한다.

| 출처 | 지위 | 표기 |
|---|---|---|
| 이 환자의 처방 정보 | 사실 | 그대로 사용 |
| 일반 약전 부작용 목록 | 참고 | **"이 환자에게 해당한다는 뜻이 아님"** 명시 |

## 5. 달력 — 올리되 메인은 아니다

**"달력을 메인으로"는 절반만 맞다.** 월 달력 그리드가 메인이면 안 된다.

1. **빈 칸이 대부분이다.** 매일 반복되는 복약은 달력에 넣을 정보가 아니다
2. **요양사는 "이번 달"을 볼 일이 없다.** 아침에 여는 화면은 "오늘"이다
3. **환자가 늘면 무너진다.** 15명이면 달력 한 칸에 안 들어간다

**결론: "오늘 할 일"이 메인, 달력은 상단에 주 단위로 압축, 월 달력은 접는다.**

달력에 표시할 것과 뺄 것:

| 넣는다 | 뺀다 |
|---|---|
| 관찰 주기 도래일 | 매일 반복되는 복약 |
| 방문 일정 (`schedules`) | |
| 이상 신호 발생일 | |

## 6. 디자인 규칙

### 6-1. 색을 세 갈래로 분리한다 (이 화면의 핵심)

| 갈래 | 색 | 역할 |
|---|---|---|
| 브랜드 | 초록 | 선택·주요 동작 |
| 상태 | 빨강 / 호박 | 급한 정도 |
| **출처** | **파랑** | **AI 관찰이라는 표시** |

**파랑을 상태색과 섞지 말 것.** 섞으면 "AI가 잡았다"가 "위험하다"로 읽힌다.
목업의 `--ai` 토큰이 이 역할이다.

### 6-2. 나머지

- 왼쪽 4px 색 띠로 급한 정도를 표시한다. 숫자를 읽기 전에 형태로 걸러진다
- 표면은 2단계까지(배경 + 카드). 카드 안에 테두리 있는 카드를 만들지 않는다
- 목업의 바탕은 청록 기미 중성(`#F7F9F8`)이다. 기존 크림 배경에서 옮긴 것이며
  초록 브랜드는 유지했다
- **접근성**: 본문 대비 4.5:1 유지, `DisplaySettings`의 글자 크기·선명하게
  설정이 계속 동작해야 한다. 정보 밀도는 낮추되 글자를 작게 하지 말 것
- 목업은 라이트/다크 토큰이 모두 정의돼 있다. 그대로 가져다 쓸 것

## 7. 작업 순서

1. **매핑 테이블 스키마 + 시드 6개 약 등록** (4-1)
2. **여정 B 역조회** — 가장 단순하고 독립적이다. 여기부터 하면 매핑이 맞는지 바로 확인된다
3. **여정 A 오늘 할 일 + 체크리스트** — `review_interval_days` 도래 계산
4. **여정 C AI 선입력** — `analysis/medication.py`의 기존 연결을 화면에 붙인다
5. **달력 재배치** (5장)
6. 약 기준표 도착 후 데이터 보강
